# JetLinks 2.1.1 到 2.11 迁移前置清单

日期：2026-06-03

## 目标

把当前已经跑通的 LSX JetLinks 2.1.1 定制功能，逐步迁移到 2.11 分支。

当前 2.1.1 本地环境应作为“可运行基准环境”保留，不要在它上面直接做 2.11 升级实验。迁移工作应使用新的分支、工作目录和数据库。

## 背景判断

前期费力对齐线上老环境，是为了找出老 `lsx-device.jar` 上的私有修改，而不是为了长期停留在 2.1.1。

直接迁到 2.11 风险很高，原因是：

- 数据库不同：老 jar 使用 MySQL，2.11 环境曾走 PostgreSQL/TimescaleDB。
- 版本跨度大：老 jar 是 JetLinks 2.1.x 私有改造，公开源码没有完全对应的 2.1.1 标签。
- 功能跨度大：客户设备、REWEB、设备任务、设备详情字段、属性上报同步、前端页面都存在私有改造。
- 运行链路复杂：设备接入不是普通 HTTP 接口，而是 MQTT 网络组件、设备网关、协议 jar、DeviceRegistry、消息处理器共同工作。
- 如果不先复现老行为，迁移到 2.11 时很难判断问题来自旧功能缺失、版本差异、数据库差异，还是迁移实现错误。

因此当前 2.1.1 的定位是：

1. 作为线上老 jar 行为的本地复现实验台。
2. 作为真实设备接入和上报的验证锚点。
3. 作为拆解私有功能的证据源。
4. 作为 2.11 迁移前的对照组。

迁移 2.11 时，不能只看代码能不能编译，还要证明业务行为与老 jar 等价。

## 功能迁移范围

优先迁移已经有证据的模块：

1. 设备 MQTT 接入链路
   - `network_config`
   - `device_gateway`
   - 协议 jar
   - MQTT 认证格式
   - 设备 deploy 到运行时 registry

2. 客户和客户设备模块
   - `CustomerController`
   - `CustomerDeviceController`
   - 客户设备查询、导入、导出、批量更新、定位、状态同步、批量 deploy

3. 设备详情扩展字段
   - `brand`
   - `model`
   - `port`
   - `subDomain`
   - `passwd`
   - `operator`
   - `switchState`
   - `syncFlag`
   - `pingAddr`
   - `pingRetry`
   - `cards`

4. 属性上报同步逻辑
   - `webpwd` -> `passwd`
   - `switch_state` -> `switchState`
   - `ping_addr` -> `pingAddr`
   - `ping_retry` -> `pingRetry`
   - SIM 卡属性 -> `DeviceCardEntity`

5. REWEB 平台侧流程
   - 前端读取 `subDomain`
   - 调用 `POST /device/instance/{deviceId}/function/reweb`
   - 打开 `http://{subDomain}.reweb.wugee.net.cn`
   - 注意：FRP 隧道建立属于设备侧或外部服务能力，不是平台 Java 代码直接完成。

6. 设备任务模块
   - `DeviceJobController`
   - 任务创建、更新、启用、禁用、删除、执行日志查询

7. 告警和场景的小改动
   - 场景变量解析
   - 场景条件列解析
   - 告警配置、记录、历史、规则绑定

暂时不要作为已确认后端功能迁移：

- 物联网卡完整平台模块 `/network/card/**`
- 当前证据显示前端存在页面，但后端 Controller 证据不足。
- 可能来自另一个 jar、另一个仓库或外部平台集成。

## 推荐迁移路线

### 阶段 0：冻结 2.1.1 基准

1. 停止对 `lsx-device-2.1.1` 做非迁移必要改动。
2. 提交或至少打包保存当前代码 diff。
3. 导出当前 MySQL 最小库。
4. 保存协议 jar、运行命令、端口、设备验证结果。
5. 把当前文档作为以后恢复入口。

### 阶段 1：建立独立 2.11 迁移环境

不要复用当前 2.1.1 数据库和端口。

建议：

- 新后端分支：`lsx-migration-2.11`
- 新数据库：例如 `jetlinks_211_migration` 或按 2.11 官方要求创建 PostgreSQL/TimescaleDB 库
- 新后端端口：例如 `18848`
- 新 MQTT 端口：例如 `18883`
- 新前端端口：例如 `15173`

这样当前 2.1.1 环境可以继续给你验证真实设备，不被迁移实验破坏。

### 阶段 2：先迁代码，不迁大量数据

先把功能代码迁到 2.11，使用最小测试数据验证：

1. 跑通 2.11 原生启动。
2. 加入 LSX 设备字段和实体扩展。
3. 加入客户、客户设备、设备任务 Controller/Service。
4. 加入属性上报同步逻辑。
5. 加入 REWEB 平台侧字段和功能调用流程。
6. 再接入协议 jar 和 MQTT 网关链路。

不要一开始导入线上 31G 数据。先用 `869624060285951` 这一台设备做端到端验证。

### 阶段 3：做数据库映射

2.1.1 老环境是 MySQL，2.11 很可能是 PostgreSQL/TimescaleDB 体系。迁移时不要直接全库导入。

需要先做映射表：

- 2.1.1 表名、字段名、类型
- 2.11 对应表名、字段名、类型
- 是否需要新建扩展字段
- 是否需要迁移历史数据
- 是否只迁配置数据

优先迁移配置类数据：

- 用户、权限、菜单
- 产品
- 协议文件
- 网络组件
- 设备网关
- 设备实例
- 客户和客户设备关系
- 设备卡片
- 规则、告警、任务配置

历史上报数据建议最后处理：

- Elasticsearch property/log indices
- session metrics
- 大体量设备日志

### 阶段 4：逐模块验收

每迁一个模块，就用固定验收项验证：

1. 后端能启动。
2. 前端页面能打开。
3. API 能返回正确字段。
4. 真实设备或模拟设备能连接。
5. 属性上报能入库和入 ES。
6. 关键页面能看到状态变化。
7. REWEB 调用能发到设备。

## 不要迁移或要重新评估的内容

不要直接迁移：

- `LocalMqttAuthDebugController` 到生产环境。
- 本地 `allowedHosts`、本地代理地址等开发配置。
- 当前只保留一台设备的本地数据库状态。
- 运行日志、临时端口、临时 PID。

需要重新评估：

- 旧协议 jar 与 2.11 的兼容性。
- MySQL 到 PostgreSQL/TimescaleDB 的表结构差异。
- 2.11 中 DeviceRegistry、协议管理、网关管理 API 是否变化。
- 前端 2.1.1 页面是否应直接搬到 2.11，还是按 2.11 新架构重写。
- 物联网卡模块后端来源。
